## Activation contract

The ordinary Next and Nest entrypoints keep their existing routes when all Showroom variables are absent. The dedicated `start:showroom` entrypoints require a complete configuration. Partial or incompatible values fail startup. The reviewed contract is `SHOWROOM_MODE=cloud-05a`, `SHOWROOM_DATA_MARKER=VANTARA_SHOWROOM_SYNTHETIC_ONLY`, an independently generated 32-byte base64url ingress key, `NODE_ENV=production`, `VANTARA_ENV=staging`, and exact HTTPS `WEB_ORIGIN` on a reserved `.example.invalid` subdomain. The reserved hostname and loopback origin listeners restrict this increment to a local test topology. A production mode flag, staging flag, or client-supplied forwarding header cannot select or authorize Showroom. Signup opt-in and populated Pilot, guest protocol, Stripe and common AI variables conflict with the mode.

Nest checks the live PostgreSQL 18 database name `vantara_showroom`, independent database comment marker, direct login as `vantara_showroom_runtime`, writable primary identity and restricted role before listening. The runtime role cannot own public tables or acquire schema/DB creation, temporary table or elevated permissions. The comment and role identify an intentionally prepared fixture target. Establishing actual data provenance and private CA/hostname verification still requires the operator review in CLOUD-05C. Next has no database credential. Its dedicated server checks the raw request target before handing it to Next. The regular Next server refuses Showroom configuration. Build the ordinary artifact first with Showroom settings absent and keep the shared policy file alongside the runtime packages. [Next custom server](https://nextjs.org/docs/app/guides/custom-server)

The offline Nginx renderer uses the same method/path allowlist. It requires a private `showroom-ingress.inc` file, containing a header override for `X-Vantara-Showroom-Ingress` with the same generated key. Store any future private include and secret out of Git and command output. Nginx replaces client input for that header and originates it to both backends. The origins match the exact Host, service and raw route independently and compare the proof in constant time. HTTP removes the proof before application handlers. Missing include blocks Nginx startup. A missing or incorrect proof leaves the origins closed. The proof is machine admission only. It grants no staff, guest, tenant or database identity. Anyone holding the proof and reaching an origin can present it, so private network reachability, service identity and key rotation remain provider gates. Administrators should take the Showroom gateway offline and stop both dedicated services to roll back. Maintain the original service configuration separately for the ordinary app and Pilot. Keep Showroom's isolated data and access history.

## Route inventory

| Request | CLOUD-05A disposition |
| --- | --- |
| GET `/`, `/onboarding`, canonical Next static JS/CSS/font/image assets | Proxy to private Next. This permits the existing entry and sign-in page through the gateway proof. Other application screens and background requests may receive 404 until individually reviewed. |
| GET `/connect` | Canonical route reaches Next. Current CONNECT-SEC-04 local conditions still deny it in staging. |
| GET `/api/health` | Exact path through gateway only. Its normal liveness response remains separate from database readiness. |
| Staff login, `auth/me` and logout | Only existing canonical methods and exact Origin rules. Existing staff cookies and RBAC remain authoritative. |
| Reservation and request reads, request PATCH, notification list/unread | Only the exact allowlisted methods, fixed paths and current CUID format. Existing tenant scoping applies. No tenant switch, signup, room management, billing, webhook or unrelated operation. |
| GET `/socket.io/?EIO=4&transport=websocket` | Exact raw upgrade route and Origin. The origin checks ingress proof on Engine.IO itself before namespace authorization. The existing `/realtime` session/RBAC check still decides subscription. This increment permits the canonical websocket-only request and rejects polling, arbitrary query fields and sid reuse. |
| Legacy `/connect/[token]`, GET `/api/connect/:token`, POST `/api/connect/:token/requests` | Denied at gateway and appropriate application origins. The policy rejects aliases before any Next or Express path normalization. |
| POST/DELETE `/api/connect-admin/reservations/:id/access`, hosted bootstrap, `/api/guest-connect/*` | Denied. Legacy issue/rotate/revoke is preserved in ordinary mode. CLOUD-05B owns hosted guest admission. |
| Unknown methods/routes, query suffixes other than exact Engine.IO transport, trailing/repeated slash, percent encoding, malformed syntax, alternative Host | Default deny, usually 404. A malformed target may receive parser-level 400. Responses omit the input and Location. |

Nginx records fixed route categories and HTTP statuses, without request-context error logs. The closed Showroom origins suppress request logging. Tests keep generated credentials and canaries in memory or a private, removed temporary directory and report fixed labels. The protected loopback tests establish only the reviewed gateway and application behavior. A managed HTTP edge can persist rejected URLs, headers or bodies before they reach these controls. ## Verification

- Offline: `node infra/staging/config.cjs check`, `node infra/staging/showroom-gateway.cjs` in a private review terminal, and `node --test infra/staging/*.test.cjs`. The renderer emits only placeholder configuration. The existing Nginx test requires `STAGING_NGINX_TEST=1` and a disposable loopback runner.
- Repository: `pnpm --filter @vantara/api exec prisma generate`, `pnpm --filter @vantara/api test`, `pnpm --filter @vantara/api build`, `pnpm --filter @vantara/web test` and `pnpm --filter @vantara/web build` using the CI placeholder origin and upstream.
- Disposable CI: [API Security CI](../../.github/workflows/api-security-ci.yml) builds Next, creates a new isolated Showroom PostgreSQL 18 database in its ephemeral service, applies the existing migrations to the empty database, then runs `node apps/api/scripts/showroom-ci.cjs`. The harness starts loopback-only Nginx, the built Next server and real Nest middleware and controllers, with synthetic staff memberships, requests and a guest cookie. The Connect, Chromium and Pilot steps use their separate databases and exercise the existing flows independently. Exact results and SHA are in the PR. No migration files are added.
- Provider first-hop persistence, exact Linux Prisma TLS verification and private networking remain **BLOCKED**. Hosted guest admission and physical phone/laptop acceptance are **NOT RUN**. See the [HTTP gate](../security/CONNECT_SEC_03_HTTP.md) and [browser harness](../security/CONNECT_SEC_04_BROWSER.md) for the existing local proof.

## Follow-up gates

1. **CLOUD-05B** requires a reviewed hosted-only admission policy, dedicated least-privilege operator issuance, reissue and expiry/revocation semantics, and real authorization tests before adding any guest endpoint. Retain explicit local-only gates for the current implementation.
2. **CLOUD-05C** requires provider evidence at the first HTTP receiver including rejected requests, headers, bodies and error/support logs, actual private TLS with the pinned Prisma CA/hostname negatives and rotation, and private origin reachability and ingress authentication. Reassess or stop if any mandatory control fails.
3. **CLOUD-05D** requires separate founder approval and budget, disposable synthetic staging, restoration/rollback rehearsals, two-tenant staff and guest flows and actual phone/laptop QR plus WSS reconnect on independent networks. Approval depends on those tests, with Pilot local and the public demo interface deferred.
