# CONNECT-SEC-04 guest browser shell

Implements [#55](https://github.com/zuitzero/Vantara-platform/issues/55) on main after PR #54. Related work is tracked in [#49](https://github.com/zuitzero/Vantara-platform/issues/49) and [#45](https://github.com/zuitzero/Vantara-platform/issues/45).

`/connect` is a dynamic Next Route Handler. It owns an isolated HTML document with a single first-party script and style block. Per-response nonces cover both. CSP denies other scripts, framing, base URLs, object embedding and native form submission. Fetch is same-origin and refuses redirects. The document has no hydration bundle, network assets, analytics or service worker registration. `/connect/[token]` continues to use its existing Next page.

The first script captures a canonical 32-byte base64url fragment and synchronously replaces the history entry with `/connect`. The initial document request precedes the script and browsers exclude the fragment from it. A query is rejected. The code stays in a closure until confirmation, then the browser sends it in JSON once. On navigation, the shell drops the code, stay view and draft, and aborts pending fetches. A restored document reloads the clean address and reauthorizes. A lost exchange response can already have consumed the code. Refresh can recover a delivered cookie, otherwise the front desk must issue a fresh code.

The browser reads stay with a JSON POST to the fixed stay path. Browsers supply Origin on this POST, including under the document's no-referrer policy with Fetch CORS mode. The existing GET and exact HTTPS Origin validation still apply. The POST accepts only an empty object and uses the same session cookie and server-derived reservation scope as GET. Request retries retain the same payload and random idempotency key in memory. History refresh recovers committed results after reload. Sign-out revokes one guest session. See the [Fetch Origin algorithm](https://fetch.spec.whatwg.org/#append-a-request-origin-header) and [Next Route Handlers](https://nextjs.org/docs/app/getting-started/route-handlers).

The shell requires a local test or development runtime, exact loopback HTTPS origin and the CONNECT-SEC-03 HTTP and candidate-policy opt-ins plus `CONNECT_GUEST_SHELL=synthetic-https-only`. The normal API listener uses plain HTTP. The disposable acceptance harness exposes only Nest TLS on loopback, mounts the real guest API there, and forwards just the shell document to a local Next process. It trusts the short-lived certificate in an isolated Chromium NSS store. The guest API verifies the database marker and DML-only role on every operation. See [Chromium certificate management](https://chromium.googlesource.com/chromium/src/+/HEAD/docs/linux/cert_management.md).

API Security CI runs the disposable PostgreSQL 18 and Nest HTTPS suite with pinned Chromium tooling, alongside the existing Pilot checks. Browser assertions cover the Next-generated CSP, mobile viewport, explicit confirmation, sanitized URL/Referer evidence, clean history, reload, browser cookies, cross-origin and tenant isolation, replay, expiry, revocation and lost-response request retry. The harness emits generic test labels and keeps generated credentials out of artifacts. Web CI separately builds Next and checks both route entries.

Product decisions remain open on how to deliver five-minute codes near arrival, front-desk reissue after expiry or a lost response, the three-device cap and access to history after checkout. The browser acceptance covers Chromium in a disposable local environment. Rollout requires the remaining browser support, ingress logging and database TLS reviews from CONNECT-SEC-03, plus independent repository visibility and history review from #55. Rollback disables the shell flag and preserves database revocations and idempotency records.
